# Карта Софии — пилот на MapLibre GL JS

Локальная веб-карта Софии: 3D-здания, дороги, поиск по адресам/улицам/районам/
населённым пунктам/транспорту/организациям, просмотр рубрик организаций и
маршрутов транспорта с остановками. Раздел построения маршрута — пока
заглушка (см. «Известные ограничения» ниже).

Данные: OpenStreetMap (© OpenStreetMap contributors, ODbL), выгрузка по
Столичной общине (София), собрано и обработано согласно
`pipeline/` (см. ниже).

## Структура

```
C:\SofiaMap\
  data\             — sofia.db (SQLite), sofia-base.pmtiles, sofia-overlay.pmtiles
  server\           — Node.js/Express: статика + API поиска поверх sofia.db
  web\              — фронтенд: MapLibre GL JS + поиск (без сборки, обычные файлы)
  web\fonts\        — шрифт для подписей на карте (см. «Поиск по адресам и подписи»)
  pipeline\         — скрипты, которыми собраны data/* (для воспроизводимости)
```

## Запуск

Нужен установленный [Node.js](https://nodejs.org) (LTS, 18+).

```
cd C:\SofiaMap\server
npm install
npm start
```

Первый запуск соберёт `data\sofia.db` из частей `sofia.db.gz.NN.part` — это
разовая операция (база не поместилась одним файлом в лимит переноса,
поэтому лежит разбитой на части; сервер сам склеивает и распаковывает её при
старте, если `sofia.db` ещё нет).

Затем откройте http://localhost:5173 в браузере.

## Что уже работает

- 3D-здания (высота из тегов OSM `height`/`building:levels`, иначе — типовая
  оценка по `building=*`), дороги, вода, зелень, административные границы,
  названия улиц и номера домов прямо на карте (см. «Поиск по адресам и
  подписи на карте» ниже).
- Поиск с теми же группами фильтров, что в референсе (moscowmap.ru):
  Всё / Транспорт / Организации, и внутри них — Адреса и дома, Улицы, Районы
  и округа, Населённые пункты, Метро, Остановки, Ж/д станции и платформы,
  Аэропорты и автовокзалы, Маршруты транспорта, Рубрики организаций.
- Панель результатов, карточка выбранного объекта, список остановок
  маршрута, просмотр рубрики организаций со списком и кластеризацией на карте.
- Клик по пустому месту карты — всплывающая карточка найденного объекта.
- Заглушка «Построить маршрут» — открывает информационную панель без
  реального провайдера (расчёт маршрутов — отдельная задача).

## Известные ограничения первой версии

- **Расчёт маршрута не реализован** — сознательно, отдельная задача.
- Мультиполигонные здания (relation) — учтены (в отличие от самой первой
  версии базы), но геометрия крыш по-прежнему плоская экструзия по высоте,
  без формы крыши (это ограничение MapLibre `fill-extrusion`, не базы).
- Привязка домов к улице без тега `addr:street` — по ближайшей линии в
  пределах 300 м (без учёта реальной топологии/одностороннего движения).
- Рубрикатор организаций — свой словарь ~200 сопоставлений; часть организаций
  попадает в общую рубрику «Прочее» (можно уточнять словарь `pipeline/rubricator.py`
  итеративно).
- Поиск — по вхождению подстроки (без морфологии): запрос должен совпадать
  с текстом названия как есть (например, «Сердика» находит все совпадения,
  но «аптека» не находит рубрику «Аптеки», т.к. подстрока не совпадает
  дословно).
- Шэринг ссылкой — сохраняются только текст запроса и фильтр (`?q=&type=`),
  не выбранный объект/масштаб/центр карты (упрощено ради времени; при желании
  можно расширить по образцу `sofia-maplibre-webmap-plan.md` §4).
- Районы (таблица `districts`) объединяют официальные 24 района Софии и
  некоторые другие административные единицы того же уровня OSM
  (`admin_level=9`) — не считывались по списку официальных названий районов,
  так что несколько лишних записей возможны.

## Пересборка данных (если нужно обновить)

Всё в `pipeline/` — исходники, из которых собраны файлы в `data/`:

1. `build_boundary.py` — восстанавливает полигон границы Столичной общины из
   сырого Overpass-ответа (`relation(7276261); out geom;`).
2. `osmium extract` по этому полигону из полного `bulgaria-*.osm.pbf` (Geofabrik).
3. `rubricator.py` + `parse_full.py` — разбор в `sofia.db` (SQLite).
4. Планетайлер по схеме `sofia-schema.yml` → `sofia-base.pmtiles`
   (здания/дороги/землепользование/вода/границы).
5. `export_overlay_geojson.py` + Tippecanoe → `sofia-overlay.pmtiles`
   (организации/остановки/маршруты/районы/населённые пункты).

Требует: `osmium-tool`, `pyosmium` (пакет `osmium` в pip), `shapely`,
Java 17+ и `planetiler.jar` (https://github.com/onthegomap/planetiler),
`tippecanoe`.

## Производительность: два раунда оптимизации (2026-09-05)

**Раунд 1 — размер тайлов.** Первая версия `sofia-base.pmtiles` отдавала
**все классы дорог** (включая служебные проезды, пешеходные дорожки,
тропинки — ~96 тыс. улиц) начиная с zoom 6, а слои землепользования —
с zoom 8, без разбивки по важности. Тайлы на «обзорном» масштабе (примерно
zoom 8–11, где здания ещё не рисуются) весили в 4–6 раз больше нормы (до
~460 КБ на тайл на zoom 10) — разбор/растеризация такого тайла при
подгрузке во время панорамирования — чисто CPU-стоимость, не сеть.
Исправлено разбивкой дорог на уровни по классу (магистрали — с zoom 6,
далее вторичные/третичные, жилые, и в последнюю очередь служебные/
пешеходные — только с zoom 15) и подъёмом порога землепользования до
zoom 10–11.

**Раунд 2 — лишние данные и «зачем эти пунктиры».** После раунда 1 задержки
остались заметны, а на близком масштабе через весь экран шли разноцветные
пунктирные линии. Разобрались: это был **всегда включённый фоновый слой
маршрутов транспорта** (все 289 маршрутов города, нарисованные прямой
линией от остановки к остановке — не по факту улиц) и **административные
границы OSM с `admin_level=9`** — оказалось, что это не одна граница
Софии, а 121 отдельный полигон (районы + другие единицы), нарисованный
поверх зданий фиолетовым пунктиром везде и всегда. Заодно проверили
`admin_level=8` — тоже не единая граница, а 73 отдельных полигона соседних
муниципалитетов. Кроме того, оверлейные тайлы (`sofia-overlay.pmtiles`)
на каждый просмотренный тайл отдавали данные организаций/районов/
населённых пунктов (20 699 точек + 161 полигон), которые в стиле карты
вообще нигде не отрисовываются — они показываются только через поиск.

Убрано (можно вернуть по частям, если понадобится):

- фоновый слой маршрутов транспорта (реальный маршрут всё ещё рисуется
  точно, когда его выбираешь через поиск — просто не висит всегда);
- слой административных границ OSM целиком — вместо него теперь один
  маленький статичный контур Столичной общины (`data/sofia-boundary.geojson`,
  ~430 точек после упрощения, 10 КБ) — та самая граница, которой изначально
  вырезались данные, а не смесь тегов `admin_level`;
- организации/районы/населённые пункты и подпись числа в кластере (вместе
  с внешней зависимостью от шрифтов `protomaps.github.io`) — из оверлейных
  тайлов;
- неиспользуемые атрибуты (`name`/`ref`/`oneway`/`surface` у дорог, `name`
  у зданий, линии рек `waterway`, которые всё равно не отрисовывались стилем)
  — оставлены только те поля, которые реально читает `web/js/map-style.js`.

Итог по объёму: `sofia-base.pmtiles` 18,8 МБ → 12,2 МБ,
`sofia-overlay.pmtiles` 5,6 МБ → 0,15 МБ. Подробности и как вернуть слои —
в `pipeline/sofia-schema.yml` (комментарии по каждому решению) и в проектном
документе `sofia-maplibre-webmap-results.md`.

**Раунд 3 — задержки остались на всех масштабах: дело не в данных.**
После раундов 1–2 карта стала визуально гораздо чище, но задержки при
панорамировании/зуме сообщались как ощущающиеся **на любом масштабе**, а не
только там, где были тяжёлые тайлы. Это значит, что причина не в объёме
передаваемых/разбираемых данных (их и так уже почти нет), а в стоимости
самого рендеринга.

Подключились напрямую к браузеру на компьютере пользователя (через мост к
устройству) и проверили WebGL напрямую:

```js
canvas.getContext('webgl').getParameter(...UNMASKED_RENDERER_WEBGL...)
// → "ANGLE (Microsoft, Microsoft Basic Render Driver (0x0000008C)
//     Direct3D11 vs_5_0 ps_5_0, D3D11)"
```

`Microsoft Basic Render Driver` — это программный (CPU) растеризатор
Windows, а не настоящая видеокарта. То есть Chrome на этой машине рисует
WebGL (а значит, и всю карту MapLibre) **без аппаратного ускорения**, на
процессоре — при 16 логических ядрах (`navigator.hardwareConcurrency: 16`,
машина явно не слабая) это почти наверняка означает, что аппаратное
ускорение в Chrome выключено или заблокировано (устаревший/проблемный
драйвер, `chrome://settings` → "Использовать аппаратное ускорение" выключено,
или ноутбук с двумя видеокартами, где Chrome назначен на встроенную/
энергосберегающую). Это объясняет задержки на любом масштабе: стоимость
софтверного рендеринга не зависит от того, сколько данных в тайле — сама
отрисовка кадра дорогая всегда.

Что сделано на стороне приложения сразу в раунде 3 (снижает нагрузку на
софт-рендерер для всех, не только для тех, у кого он программный):
- по умолчанию плоский вид (`pitch: 0` вместо `45°`) — наклонённая камера
  заставляет MapLibre рисовать намного больший участок земли позади
  видимой области, чем плоский вид того же размера;
- отключено сглаживание (`antialias: false`) — на софтверном рендерере это
  ощутимо дороже;
- ограничен `pixelRatio` (не выше 1.5, а в `lite`-режиме раунда 4 — не выше 1)
  — на экранах с масштабированием Windows >100% канвас иначе рисуется в
  2 раза больше пикселей, чем видно на экране.

Раунд 3 предполагал, что дальше пользователю нужно самому включать
аппаратное ускорение в браузере/Windows (см. шаги ниже) — рабочий вариант
для одного конкретного компьютера, но не для сервиса на широкую аудиторию:
нельзя рассчитывать, что каждый посетитель станет разбираться в
`chrome://settings` или сможет вообще что-то изменить (корпоративная
политика, отсутствие прав администратора). Раунд 4 ниже снял это
допущение — приложение определяет программный рендеринг само и
подстраивает стиль карты, без участия пользователя. Шаги ниже остаются
полезными для тех, кто **хочет** получить полный 3D-режим на своей
машине, но их выполнение больше не обязательно для того, чтобы карта
нормально работала:
1. Открыть `chrome://gpu` и посмотреть строку `WebGL` в "Graphics Feature
   Status" — если написано "Software only, hardware acceleration
   unavailable", смотреть раздел "Problems Detected" — там будет причина.
2. `chrome://settings/system` → включить "Использовать аппаратное ускорение
   графики, если доступно" → перезапустить браузер.
3. Если ноутбук с двумя видеокартами (например, встроенная Intel +
   дискретная NVIDIA/AMD) — в Windows: Параметры → Дисплей → Графика →
   добавить `chrome.exe` → назначить "Высокая производительность", и
   обновить драйвер видеокарты через Диспетчер устройств/сайт
   производителя.
4. Если карта открывается через удалённый рабочий стол/VNC/облачную
   Windows-сессию — там аппаратное ускорение GPU часто недоступно в
   принципе; в этом случае карта останется в `lite`-режиме и это ожидаемо.

**Раунд 4 — приложение само подстраивается под софтверный рендеринг.**
Раунд 3 объяснил причину задержек, но решение получалось «пользователь
должен включить аппаратное ускорение сам» — а карта делается для широкой
аудитории: заставить каждого посетителя лезть в `chrome://settings` и
разбираться с настройками видеокарты нереально (корпоративные ноутбуки
с отключённым GPU-ускорением по политике безопасности, устаревшие/
заблокированные драйверы, виртуальные машины и облачные Windows-сессии,
удалённый рабочий стол — во всех этих случаях у человека нет возможности
это исправить, даже если ему объяснить как).

Поэтому вместо инструкции пользователю добавлена автоматическая проверка
на стороне приложения:

```js
// web/js/map-style.js
function detectRenderQuality() {
  // пробует получить WebGL-контекст и его renderer-строку
  // (WEBGL_debug_renderer_info) — если в ней есть сигнатура известного
  // софтверного растеризатора (SwiftShader, "Basic Render Driver",
  // llvmpipe, Mesa OffScreen, Software Rasterizer, softpipe) — возвращает
  // "lite", иначе "full"
}
```

Результат подставляется в `buildStyle(quality)` при инициализации карты
(`map-search.js`):

- **`full`** (обычное аппаратное ускорение) — всё как раньше: 3D-здания
  (`fill-extrusion`), можно наклонять камеру (`maxPitch: 60`).
- **`lite`** (обнаружен софтверный рендеринг) — здания рисуются плоской
  заливкой (`fill`) тем же цветом по типу, без объёма и без стоимости
  боковых стен/освещения; наклон камеры физически заблокирован
  (`maxPitch: 0`), чтобы нельзя было случайно перетащить карту в дорогой
  3D-вид; чуть туже ограничен `pixelRatio`. Данные, сервер, все остальные
  слои и весь поиск — идентичны обоим режимам, меняется только отрисовка.

Проверка полностью автоматическая и без участия пользователя — никакого
баннера «включите GPU» нет, это не то, на что многие посетители способны
повлиять. Какой режим выбран для конкретного визита, видно в консоли
браузера (F12 → Console): `[map] render quality: full` или `... lite`.

Статус проверки на 2026-09-05: код синтаксически проверен и прогнан в
headless-браузере песочницы (там всегда программный рендеринг — он и
показал `lite`-режим с корректной отрисовкой всех слоёв, включая плоские
здания, без ошибок).

**Раунд 4b — дожали ещё немного, после отзыва «объёмность пропала, стало
быстрее, но плавности при зуме всё ещё не хватает».** Прямая попытка
профилировать реальный браузер пользователя через автоматизацию (Claude in
Chrome) уперлась в тот же артефакт, что и в раунде 3: автоматизированная
вкладка находится в фоне (`document.visibilityState: "hidden"`), а в этом
состоянии Chrome сам приостанавливает WebGL-рендеринг независимо от кода —
значит, замерить реальный FPS отсюда нельзя, только по ощущениям
пользователя в его настоящем активном окне. Вместо замера — три
дополнительные, безопасные по эффекту правки по известным особенностям
MapLibre:

- `fadeDuration: 0` (было по умолчанию 300 мс) — MapLibre без этого
  кросс-фейдит старое и новое поколение тайлов друг с другом почти треть
  секунды на каждый шаг зума, то есть **в момент, когда зум и так самый
  дорогой кадр, рисуются оба слоя тайлов одновременно**. Отключено для
  обоих режимов — визуального смысла в этом плавном переходе для этой
  карты нет, а стоимость есть;
- в `lite` убран слой обводки дорог (`roads-casing`, белая линия под
  цветной) — у дорог была двойная заливка (обводка + сама линия) на каждый
  пиксель дороги, сейчас только одна;
- в `lite` здания появляются на zoom 14, а не 13 — на один уровень позже,
  чем раньше, именно в том диапазоне зума, где чаще всего идёт колёсико
  мыши/зум-жест;
- в `lite` наклон и поворот камеры отключены полностью на уровне
  интеракций (`dragRotate`/`pitchWithRotate`/`touchPitch: false`,
  компас скрыт), а не только ограничены — раз наклон и так недостижим
  (`maxPitch: 0`), не тратим кадр на пересчёт вращения вообще.

Смоук-тест в песочнице (Playwright, серия колёсико-зум событий, 12 шагов) —
без ошибок, все слои рисуются корректно (см. скриншот в истории задачи).
Доставлено и подтверждено побайтовым совпадением размера файла
(`device_list_dir`).

**Честно про потолок**: дальше в рамках векторного рендеринга выжимать
почти нечего — сняты все крупные "рисуем на весь экран дважды" источники
затрат, которые были видны без профилирования. Программный (CPU)
растеризатор всё равно кладёт снизу платформенный минимум стоимости кадра
на пиксель — это не устраняется дальнейшей чисткой векторных слоёв. Если
после этой правки всё ещё ощутимо не хватает плавности и это критично —
следующий шаг качественно другой: **растровые тайлы** (сервер один раз
заранее рендерит PNG-картинки тайлов, клиент в `lite`-режиме просто
показывает готовые картинки вместо векторной отрисовки каждый кадр) — это
именно то, как работали карты до эпохи GPU-рендеринга, и это единственный
способ получить по-настоящему одинаковую скорость на любом железе
независимо от GPU. Это отдельная по объёму задача (нужен headless-рендерер
для предгенерации тайлов), не правка на 20 минут — стоит обсуждать отдельно,
если текущего результата всё ещё не хватает.

## Поиск по адресам и подписи на карте (2026-09-05)

Пользователь сообщил о двух проблемах сразу: поиск по адресам не работал, и
на самой карте не было ни названий улиц, ни адресов/номеров домов (только
через поиск, и то не работавший для адресов).

**Баг №1 — поиск по адресам молчал.** Запрос вида «Оборище 5» должен искать
дом 5 по улице Оборище, но SQL-запрос сравнивал ВСЮ строку запроса целиком
и с названием улицы (`addr_street`), и с номером дома (`housenumber`) — то
есть требовал, чтобы столбец `housenumber` (там просто хранится «5»)
содержал в себе буквально «Оборище 5» целиком. Это никогда не совпадало ни
при каком запросе с номером дома — сработать мог только резервный вариант
(совпадение с названием самого здания, `name`, если оно было), поэтому
поиск адресов с номером дома не находил вообще ничего, а поиск без номера
(только улица) тоже не срабатывал по той же причине. Исправлено в
`server/src/routes/search.js`: запрос теперь сам разбирает ввод на «часть
улицы» и «часть с номером» (по последнему числовому токену в конце строки)
и матчит каждую часть со своим столбцом отдельно; если номера в запросе нет
вообще — просто ищет по названию улицы/здания, без требования совпадения
номера. Проверено (после фикса): «Туше Делииванов 5» находит ровно этот
дом, «Оборище» без номера находит 12 домов на этой улице, заведомо неверный
номер («Туше Делииванов 99») корректно не находит ничего.

**Проблема №2 — на карте не было подписей.** Раунд 2 оптимизации
производительности убрал единственный текстовый слой (подпись числа в
кластере поиска) вместе с внешним хостом шрифтов
(`protomaps.github.io/basemaps-assets`), который 404-ил в песочнице — и с
тех пор на карте вообще не было текста: ни названий улиц, ни номеров домов
(это никогда и не было реализовано отдельно от того убранного слоя).
Решение — не тот же внешний хост, а свои файлы шрифта:

- В `web/fonts/Noto Sans Regular/` лежат три небольших файла (~290 КБ
  суммарно) — это шрифт в специальном протобуф-формате, который MapLibre
  использует для отрисовки текста на карте (не обычный `.ttf`/`.woff`).
  Собраны один раз из открытого набора `protomaps/basemaps-assets`
  (Noto Sans, лицензия OFL) — только диапазоны символов, которые реально
  нужны болгарским названиям: латиница и кириллица. Никакого обращения к
  внешнему хосту в рантайме больше нет — файлы отдаются тем же сервером,
  что и всё остальное.
- `pipeline/sofia-schema.yml` — добавлен атрибут `name` в слой дорог (кроме
  самого нижнего яруса — служебные проезды/тропинки почти никогда не имеют
  названия в OSM, добавлять его туда — это только лишние байты без
  надобности) и атрибут `housenumber` в слой зданий (тег `addr:housenumber`
  напрямую на здании — есть у ~39 500 из 132 920 зданий; это визуальная
  подпись на карте, а не тот более сложный алгоритм с привязкой к
  ближайшей улице, который использует `sofia.db` для поиска — для подписи
  на карте достаточно прямого тега). `sofia-base.pmtiles` пересобран
  Planetiler, вырос с 12,2 МБ до 13,1 МБ.
- `web/js/map-style.js` — два новых слоя: `road-labels` (подписи улиц вдоль
  линии дороги, размер текста зависит от класса дороги и масштаба,
  показываются с zoom 12 в «полном» режиме / 13 в «lite») и
  `address-labels` (номера домов, только с zoom 17/18 — на любом более
  далёком масштабе это была бы каша из тысяч цифр, а не подпись). Раскладка
  текста и проверка на перекрытие у MapLibre считается в фоновом потоке
  (Web Worker), а не в кадровом цикле рендеринга — то есть это не
  возвращает проблему с рывками при зуме, которую решали раунды 3-4.

Проверено в песочнице (Playwright): полный цикл поиск → выбор адреса с
номером дома → подсветка правильного здания на карте → отображение подписи
номера дома на нём; названия улиц читаются вдоль дорог на скриншоте.
Файлы доставлены и подтверждены побайтовым совпадением размера
(`device_list_dir`): `sofia-base.pmtiles`, `map-style.js`, `search.js`,
`sofia-schema.yml`, три файла шрифта.

**Дополнение — крупные улицы не подписывались на обзорном масштабе, и не
было названий кварталов.** Пользователь прислал скриншот обзорного вида
города (масштаб, на котором виден весь город, вроде дефолтного при
открытии карты) без единой подписи: ни Околовръстен път, ни бульваров, ни
названий районов вроде «ж.к. Младост». Причина — первая версия
`road-labels` была ОДНИМ слоем с одним общим `minzoom` (12) для всех
классов дорог сразу: у магистралей название появлялось бы одновременно с
названием последнего переулка, то есть только когда всё равно уже поздно
(на обзорном масштабе — никогда). Настоящие карты подписывают кольцевую и
бульвары значительно раньше, чем дворовые проезды.

Исправлено:

- `road-labels` разбит на 4 слоя по классу дороги (`ROAD_LABEL_TIERS` в
  начале `web/js/map-style.js`) с разным `minzoom`: магистрали/трассы — с
  zoom 8, первичные дороги — с 10, вторичные/третичные — с 12, жилые/
  местные — с 13 (как и раньше). У каждого яруса свой размер текста —
  крупнее для более значимых дорог, чтобы визуальная иерархия совпадала со
  смысловой.
- Добавлены названия кварталов/жилых комплексов (2026-09-05) — то, что
  пользователь назвал «названиями кварталов»: в OSM это отдельные точки с
  тегами `place=suburb/quarter/neighbourhood` (216 штук в этой выгрузке —
  «ж.к. Младост 1», «ж.к. Люлин 6», «кв. Горна баня» и т.п., не то же
  самое, что официальные 24 района или квартальная сетка застройки).
  Новый слой `place` в `pipeline/sofia-schema.yml` (только точки — у части
  этих названий в OSM ещё и отдельная граница-полигон с тем же именем,
  дублировать подпись не нужно), новый слой `place-labels` в
  `web/js/map-style.js`: крупный текст заглавными буквами, с zoom 10, и
  специально размещён в стиле ПЕРЕД слоями `road-labels`, чтобы при
  конфликте занимаемого места название квартала имело приоритет над
  названием улицы (MapLibre отдаёт место тому, что расположено раньше в
  списке слоёв).

`sofia-base.pmtiles` пересобран (13,1 МБ → 13,2 МБ — 216 точек почти ничего
не весят). Проверено скриншотом на дефолтном обзорном масштабе (zoom 12) —
и магистрали, и кварталы теперь читаются сразу при открытии карты, без
необходимости зумиться. Доставлено и подтверждено побайтовым совпадением
размера: `sofia-base.pmtiles`, `map-style.js`, `sofia-schema.yml`.

## Наведение на объекты: подсветка, курсор, попап (2026-09-05)

Запрос: «При наведении на контуры дома, линию улиц, название районов и
аналогичные действия по схожим по логике объектам: 1. подсвечиваем контуры
объекта. 2. Меняем курсор с ладони на палец. 3. Выводим попап с основной
информацией и ссылкой на страницу объекта». Реализовано для зданий, линий
улиц (и их подписей), названий кварталов и остановок транспорта — всё, что
уже было интерактивным слоем на карте.

**Архитектура.** Чисто фронтенд, без изменений на сервере и в данных:

- Новый geojson-источник `hover` в `web/js/map-style.js` (тот же приём, что
  уже использовался для `selected` — подсветки выбранного результата
  поиска) и два новых слоя поверх всех остальных: `hover-outline` (`line`;
  MapLibre умеет рисовать этим типом слоя контур и Polygon/MultiPolygon
  геометрии тоже, не только LineString — этим одним слоем накрыты и контуры
  зданий, и линии улиц) и `hover-point` (`circle`, для точечных объектов —
  названий кварталов и остановок). Цвет — свой синий (`#2f7dd6`), не
  красный `selected`: наведение временное/исследовательское, выбор —
  осознанное действие пользователя, визуально они не должны путаться.
- В `web/js/map-search.js` — обработчик `mousemove`, поставленный на
  `requestAnimationFrame`-троттлинг (не чаще одного `queryRenderedFeatures`
  за кадр, независимо от частоты событий мыши): это тот же принцип
  бережного отношения к кадру, что и весь предыдущий раунд оптимизации под
  software-рендеринг («lite»-режим) — на слабой машине лишний
  `queryRenderedFeatures` на каждый пиксель движения мыши был бы ощутимой
  нагрузкой.
- Курсор: `map.getCanvas().style.cursor = "pointer"` на наведённом объекте,
  сброс в `""` при уходе — тот же приём, что в официальных примерах
  MapLibre/Mapbox.
- Попап: один переиспользуемый `maplibregl.Popup`, без кнопки закрытия.
  Для зданий и остановок в тайле намеренно нет названия (см.
  `pipeline/sofia-schema.yml` — «name» не добавляли, чтобы не дублировать
  то, что и так даёт SQL), поэтому попап для них дозапрашивает то же
  `/api/hit-test`, которым уже пользовался клик по пустому месту на карте.
  Для улиц и кварталов название уже есть прямо в тайле — без сетевого
  запроса.

**Клик = то же действие, без необходимости попасть мышью в попап.**
Первая версия делала действие («Подробнее»/«Найти на карте») кликабельной
ссылкой только внутри самого попапа — и здесь всплыла реальная проблема
плотной застройки: попап рисуется со сдвигом от точки наведения (чтобы не
закрывать сам объект), и на скриншотах пилотного тестирования путь мыши к
кнопке пересекал соседние здания, каждое из которых перехватывало
наведение на себя, а то и просто пустой промежуток между зданиями — попап
исчезал раньше, чем курсор до него доходил. Решение: обычный клик прямо по
подсвеченному объекту (там, где курсор уже стоит, без дополнительного
движения мыши) выполняет то же самое действие. Кнопка в попапе осталась
как более быстрый путь, когда до неё удаётся дотянуться, но обязательной
она больше не является.

**«Страница объекта».** Отдельных страниц объектов в проекте пока нет
(«Страниц сейчас нет, планируем» — из формулировки задачи), поэтому
сегодняшний стенд-ин выбран из того, что уже есть в приложении:

- адрес/дом, организация, остановка — та же карточка с деталями, что
  открывается при выборе результата поиска (`apiObject` + существующий
  `renderSelected`/`choose()`);
- улица — не отдельная карточка (у сегментов дороги на карте нет id из
  таблицы улиц в sofia.db), а поиск по имени улицы — тот же путь, что и
  ручной ввод в поисковую строку;
- квартал/жилой комплекс (`place-labels`) — для них в принципе нет объекта
  в базе (это только точка-подпись из OSM, без своей карточки), поэтому
  попап честно говорит «Страница появится позже» вместо фиктивной ссылки —
  та же условность, что уже применена к заглушке построения маршрута.

Изменённые файлы: `web/js/map-style.js` (источник `hover` + 2 слоя),
`web/js/map-search.js` (вся логика наведения/клика), `web/css/map-search.css`
(стили попапа наведения). Сервер не перезапускать — это фронтенд, обновления
файлов подхватываются обычным `express.static` при обновлении страницы в
браузере (см. предыдущий раздел про перезапуск сервера — там речь шла
именно о серверном коде, не об этом).

## Наведение на объекты — доработка по трём замечаниям (2026-09-05)

Три замечания по предыдущему разделу: (1) улицы разбиты на сегменты — при
наведении подсвечивался только один, а не вся улица с названием; (2) попап
должен появляться только после долгого (>5с) наведения, а исчезать — после
такого же наведения на другой объект либо по клику; (3) синий цвет не
подходит — для зданий вместо контура нужно изменение оттенка, для улиц и их
названий — увеличение ширины/шрифта при наведении. Реализовано всё три;
механизм подсветки поменялся полностью (текст раздела выше — про первую
версию, оставлен для истории).

**Механизм подсветки — `feature-state`, не отдельный geojson-слой.**
Через временный debug-хук и Playwright проверено, какие слои тайлов несут
стабильный числовой id объекта: здания/дороги/`place-labels` (кварталы) в
`sofia-base.pmtiles` — несут; точки остановок в `sofia-overlay.pmtiles` —
нет (везде `id: null`, тайлы собирались Tippecanoe, а не Planetiler).
Поэтому для зданий/дорог/подписей/кварталов теперь используется нативный
`map.setFeatureState({source, sourceLayer, id}, {hover})`, который управляет
paint-выражениями напрямую; для остановок — по-прежнему отдельный geojson-
источник (единственный случай без стабильного id).

**Все сегменты улицы разом.** Дороги в OSM почти всегда разбиты на десятки
ways (проверено: у одного бульвара — 19 сегментов в одном экране).
Подсветка теперь ищет через `queryRenderedFeatures` все сегменты с тем же
`name` во всей видимой области (не только под курсором) и включает
`feature-state` у всех разом одним пакетом вызовов; так как линия дороги и
её подписи используют один и тот же `{source, sourceLayer, id}`, одна и та
же пачка одновременно подсвечивает и линию, и все подписи этой улицы.

**Попап с задержкой 5с и гистерезисом.** Разделены два состояния: что под
курсором прямо сейчас (мгновенно двигает подсветку/курсор) и что
подтверждено в попапе (появляется только после непрерывных 5000 мс
наведения на один объект; смена объекта сбрасывает таймер). Короткий
проход через промежуток без объекта не прячет уже подтверждённый попап —
полезный побочный эффект того же разделения состояний, особенно в плотной
застройке. Клик мгновенно убирает попап независимо от таймера. Появление —
плавное (300ms CSS opacity-transition), скрытие/замена — мгновенные.

**Без синего; оттенок у зданий, ширина+шрифт у улиц.** У зданий контур
убран целиком, вместо него — затемнение заливки на hover (per-type цвет ×
0.86 по каждому каналу RGB, посчитано скриптом): например церкви `#c9b8a8`
→ `#ad9e90`, школы/больницы `#b9c6d6` → `#9faab8`. У улиц `line-width`
увеличивается на hover — обычное paint-свойство, без ограничений. С
подписями пришлось обойти реальное ограничение MapLibre: `feature-state`
работает только в paint-свойствах, а `text-size` — layout-свойство (сама
попытка даёт ошибку валидации стиля: `"feature-state" data expressions are
not supported with layout properties`). Решение — подмена: реальная подпись
гасится через `text-opacity` (paint) до 0, а рядом отдельный
JS-заполняемый geojson-источник (`hoverLabel`) рисует ту же
надпись/геометрию увеличенным ФИКСИРОВАННЫМ размером через два новых слоя
(`hover-road-label`, `hover-quarter-label`). Остановки перекрашены в
янтарный `#c9781f`, ссылка в попапе — в `#a8631a`; синего цвета в подсветке
больше нигде нет.

**Проверено** (Playwright, sandbox): 0 ошибок в консоли; 19/19 сегментов
тестовой улицы подсвечиваются разом вместе с подписями; попап появляется
не раньше ~5с и не позже ~5.6с, переживает короткий проход через
промежуток, требует полных 5с на новом объекте перед подменой, исчезает
мгновенно по клику; скриншоты подтвердили затемнение заливки здания без
контура и заметно расширенную линию+подпись бульвара при наведении.

Изменённые файлы: те же три, что и в разделе выше (`map-style.js`,
`map-search.js`, `map-search.css`). Чисто фронтенд, перезапуск сервера не
требовался.

## Технологии (решение зафиксировано в проекте)

MapLibre GL JS (клиент) + PMTiles (раздача тайлов статикой, без сервера
тайлов) + Planetiler/Tippecanoe (генерация тайлов). Подробности и обоснование
выбора — в документе проекта `rendering-tech-decision-2026-09-05.md`.
